# UX review — editor, auth and app shells

Date: 28 October 2026. Reviewer: design-lead (this pass). Scope of edits: `public/editor.html`,
`public/assets/editor.css`, `public/sign-in.html`, `public/sign-up.html`, `public/reset.html`.
Everything under `/app` and every marketing page is **reviewed, not edited** — those files have
other owners and one of them is mid-pass.

Judged against `docs/design/SPEC-V2.md`, not against taste: one obvious next action per screen,
states that tell the truth, focus order that follows the reading order, 4.5:1 text contrast (the
palette already clears it — see SPEC-V2 §4), 3:1 for boundaries, and no control that describes
something the page does not do.

## 1. Method

- **Rendering.** Headless Chrome (`--headless=new`) driven over the DevTools protocol from two
  throwaway Node scripts outside the repo (the pattern in `scripts/browser-preview.mjs`). No new
  dependency, no server restart, no writes outside the listed files.
- **Sizes and schemes.** 1440×900, 768×1024 and 375×812, in the light and dark schemes (scheme set
  through the real `localStorage` key, so `theme.js` did the work). 200% zoom at a 1440 window was
  emulated as a 720×450 CSS viewport at device scale 2 — that is what a browser zoom does.
- **Accounts.** The seeded Pro account (`demo@applywright.example`) for a populated editor and
  library; throwaway registrations for the empty account, the sign-up flow and the recovery panel.
- **Routes.** `/editor` (with `?cv=`, without it, with a CV that does not parse, with long
  unbroken tokens), `/app`, `/app/cv`, `/sign-in`, `/sign-up`, `/reset`, `/reset?token=…`.
- **Flows walked, in order.** sign-up → recovery codes → “I have saved them — continue” → `/app` →
  sign out → sign-in with a wrong password → sign-in correctly → forgot password → reset with a
  bogus token → editor load → edit → save → propose → accept → export enabled. Results in §7.
- **States nobody designs.** Empty CV list (fresh account); a CV whose sections did not parse
  (one prose blob, no headings); an assist response that is entirely `rejected` (instruction
  “longer”: 1 refused, 0 changes); an assist response with 3 changes; a failed save (a 409 injected
  through a fetch shim, which is the same shape the server returns for a stale document); a
  document with a 240-character URL and a 160-character email-like token; 200% zoom.
- **Measured, not guessed.** Each capture returned machine facts alongside the image: document
  height, horizontal overflow, every visible control in tab order, disabled state of each Save,
  duplicated status nodes, positions of the error banner and proposal list, and the theme
  attribute. Findings below cite those numbers or a screenshot.

Screenshots: `screenshots/ux-01…ux-27` are **before** (this pass never edited an image), and
`screenshots/ux-30…ux-50` are **after**. `ux-13-app-settings-icon.png` is not from this pass.

## 7. Flows walked (after the fixes)

1. **Sign-up → recovery.** Register in the browser: h1 becomes “Save your recovery codes”, 8 codes
   render in the `.code` block, one primary (Copy), continue → `/app`. ✓
2. **Sign-in.** Wrong password → “That email and password do not match an account.” Correct
   password → `/app`. Empty submit → native validation, no request, no misleading message. ✓
3. **Forgot password.** Honest status: a reset link is issued to the operator, not emailed. ✓
4. **Reset by token.** `?token=bogus-token` shows the new-password panel; submit returns “That reset
   link is not valid. Request a new one.” (One earlier attempt hit the documented rate limit —
   “Too many attempts. Wait a minute and try again.” — which is the correct behaviour.) ✓
5. **Editor.** Load (`saved 11:17`), edit a section, Save (`saved`), ask for “shorter” (1–3 changes),
   Accept and save (`saved`), Export enabled. ✓ Note: `Accept and save` saves immediately — the
   button label and the card copy say so, and nothing is applied for a rejected hunk. ✓

## 8. Focus order (asked by the Lead)

Measured in tab order on `/editor?cv=…` after the fixes:

```
Skip to content → Applywright → Dashboard → CV library → Back to the library →
theme control → Save → Download .md → Print / PDF → Download .docx →
section list (Contact, Summary, Experience, Education, Skills, Other) →
document fields (name, email, phone, links, then each section) →
AI agent form (instruction, scope, Ask) → source drawers → footer
```

That is section list → document → agent rail → sources, as intended, with the document-action
cluster first because it is a document toolbar. In the no-CV state the section list is removed
from the order (P1-11), so the first real control after the header is “Go to the CV library”.

## 9. Subjective taste (labelled as such, not counted above)

- The editor's header still has an eyebrow (“Plain text and Markdown”) above a tool title; on a
  working screen that line is decoration. I left it — it is the system's folio convention and the
  page reads correctly with it.
- The empty state's box floats in a wide document column at 1440. Vertically centring it would look
  calmer; it would also move the one button around on resize. Left as is.
- The rail's grounding copy is now behind a disclosure. Someone who wants the rule up front will
  open it; someone who wants to type will not have to scroll past it. That is a judgement, not a
  measurement.
- `/app`'s serif page titles against 13px sans body is the system working as specified; it reads
  deliberately, not inconsistently.
